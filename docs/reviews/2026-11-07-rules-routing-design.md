# Rules 自动路由设计评审（2026-11-07）

状态：**设计评审，未实现**。标准 §7 与本文一致：Rules 表存在、schema 已登记，
但运行时零代码引用；自动路由单独立项，不在本轮 v3.5 范围内。

## 1. Rules 原本要解决什么

建单方不指定 `--to/--cap` 时，谁来决定任务去哪。设想中的规则形态：按任务的
Source、标题/参数关键词、发起节点，匹配出 Target_Node 与 Skill_ID，让「只说
要做什么」的发起方不必懂全网能力分布。

## 2. 为什么一直没实现（复盘）

- **现行建单路径已经够用**：`lah task create` 有名片自动解析——按 Skill_ID
  或 Cap_ID 在 AgentCards 里挑可用名片（停派/offline 拒绝），发起方只需知道
  「要什么能力」，不必知道节点名。剩下真正需要路由判断的场景很少。
- **规则引擎是内核膨胀的入口**：匹配语义（优先级、冲突、通配、参数条件）
  一旦进内核，薄壳原则就破了；且规则表在总线上，任何持写权限者改规则即可
  改全网流量走向，治理面比收益大。
- **可观测性**：任务为什么去了 A 不去 B，必须能从业内留痕回答；隐式路由会让
  排障多一层「规则当时是怎么匹配的」考古。

## 3. 三个可选形态

| 形态 | 做法 | 代价 |
|---|---|---|
| A 不做 | 维持名片自动解析＋显式 --to/--cap | 发起方需知道 Skill_ID；跨域编排靠发起方 Agent 自己判断（现状，与「Agent 当编排者」的定位一致） |
| B 建单侧软路由（推荐） | `lah task create` 未指定目标时，读 Rules 给出**建议**并在建单回执中标明命中规则（写进 instruction 的 DataPart 留痕），最终 Target 仍是普通字段值 | 规则只影响建单瞬间，内核零改动；规则错了只错一单且可查 |
| C 内核硬路由 | 守护/枢纽在 submitted 阶段按 Rules 改 Target_Node 再放行 | 状态机多一段「待路由」语义、全网行为受规则表支配、审计与回滚都变重 |

## 4. 建议

采用 **A 为默认、B 为可选增强**，不做 C。理由：本项目的编排智能放在发起方
Agent（hub 本尊）身上是既定定位（标准 §0：hub 是逻辑角色、负责拆解派发），
路由表替代的是 Agent 的判断，而 Agent 的判断可解释、可纠正；B 只把规则降为
「建单建议＋留痕」，保留人的最终可见性。若未来出现「无人值守的定时任务需要
按内容分发」的硬场景，再评估 B 的落地：规则字段只用 Rules 现有列，不新增
字段；命中与未命中都在建单回执与首条 instruction 中留痕。

## 5. 与本轮改动的关系

v3.5 已把 Rules 从「setup 建表清单」语义中摘清（表保留、标准标注未启用），
doctor 契约检查不查 Rules（FeishuBus 不认此表）。本评审定案前，不写任何
Rules 运行时代码。
