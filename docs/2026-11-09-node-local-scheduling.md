# 定时调度改版设计：调度归节点（标准修订草案）

> 状态：机主于 2026-11-09 拍板，本草案为实现依据；实现完成时并入 `docs/standard.md`（建议版本 v3.6）。
> 取代范围：standard.md §7「定时调度（v3.5.2 新增，v3.5.4 修订）」全段，及 §10.1 第 7 条中计划型调度的部分。不动表结构、不新增列。

## 1. 背景与问题

现行机制：Rules 表兼作全网计划表，时钟只在 hub——hub 每轮扫表发现期次到达后建单，目标节点被门铃唤醒（或轮询对账）后认领执行。两个实测问题：

- **延时链长**：扫表发现（等轮次）→ 建单 → 节点唤醒 → 认领 → 执行，五段串行。生产实测：2026-11-09 晨间自检计划 08:50 触发，适逢 hub 所在 VM 于 08:47 被平台整机替换，任务 09:05 才落表；常态下完成时间也普遍晚于计划点 5 分钟以上。
- **单点错位**：全网唯一的时钟挂在全网最不稳定的主机上（hub 所在 VM 平均约 2 小时被整机替换一次，自愈最坏约 20 分钟），而执行节点（如 mac-mini）稳定性远高于它。

结论：发起权应与执行权同地——谁执行，谁计时。

## 2. 决策（机主口径，定版）

1. **调度是 node 角色的组件**：计划挂在执行节点本地，节点到点自触发、自执行。
2. **hub 角色不再发起任何定时单**，包括给它自己 node 角色的单。hub 进程内的 node 角色与其它节点完全同权：本地挂载、本地触发、本地执行。
3. **中台（总线账本）只记录**：每次运行的开始、进展与结果以现行任务格式入账；可见性、统计、看板口径不变。
4. **同一计划多节点挂载 = 各节点各执行一份**，这是设计语义、不是异常。防重只防同一节点对同一期次的重复触发。
5. **错过只补最近一期**，沿用现行语义。
6. 节点执行不了时（如关机、睡眠），该期任务在任何架构下都执行不了，本设计不为此引入额外的代偿机制；节点死活由 AgentCards 心跳独立可见。

## 3. 本地计划（节点侧）

- **存放**：节点配置目录新增 `schedules.json`（不进仓库、不进总线）。每条计划字段：
  - `id`：节点内唯一，建议沿用现有命名（如 `SCHED-HUB-MORNING`）；
  - `enabled`：布尔；
  - `cron`：五段 cron 表达式；
  - `cap`：本节点能力名，必须在本节点 commands.json 中存在（doctor 校验）；
  - `text`：指令正文；
  - `approval_class`（可选）：语义同现行，见 §5。
- **时区与期次**：沿用 `node.json` 的 `tz`（IANA 名，缺省 Asia/Shanghai），期次只按该时区墙钟计算，与宿主机时区、`TZ` 环境变量无关；期次键偏移格式与 v3.5.4 一致（`±HHMM`）。非法 `tz` 记日志并停用本地调度，守护进程不退出。
- **水位线**：本地状态文件（如 `schedule_local_state.json`，置配置目录）记「id＋cron 文本」基线与 `last_fired`。新建计划、cron 文本变化、或状态文件缺失/损坏时，首次检查只锚基线、不触发，从下一期起触发（与现行基线语义一致，仅存放位置由 hub 改为节点）。状态文件写失败记日志，该轮不触发。

## 4. 触发与入账

守护主循环内做本地调度检查（检查间隔由实现定，但正常情况下触发偏差须 ≤60 秒）。期次到达时：

1. 先写 instruction Message＋Parts（正文＝计划 `text`，Source=`cron`）；
2. 写 Tasks 行：From_Node＝To_Node＝本节点，Claimed_By＝本节点，Status 直接置 `working`（自触发即自认领，不经 submitted 排队）；Idempotency_Key＝`sched:<Node_ID>:<Schedule_ID>:<期次键>`；
3. 按 cap 的执行模板在本机执行（direct / inbox 走现行执行层）；心跳、Runs、回执、终态回写全部沿用现行链路。唯一与普通任务的区别：发起方与执行方是同一节点。

其他约定：

- **双保险防重**：触发前先按 Idempotency_Key 查总线，已有同键行则跳过（防守护重启后对同一期重复触发）；本地水位线与总线幂等键并用，与现行口径一致。
- **开机补期**：守护每次启动先跑一轮本地调度检查：存在已过期的最近一期未触发则立即补触发一次；更早的历史期次不补。

## 5. 审批与既有边界不变

- 本地触发不绕过审批：cap 或计划声明 approval_class 时，任务仍先入 `auth-required` 走现行审批流（hub 枢纽回调校验操作者为机主），驳回即 canceled、不执行，批准后才执行。
- 单位节点「只出不进」等既有边界不变。本地计划文件只由节点本机维护，不经总线下发、不由 hub 远程修改。

## 6. hub 角色的变化

- **停止**：按 Rules 计划行建单（§7 调度职责与 §10.1 第 7 条的计划型部分作废）。
- **保留**：审批回调、回执呈递、陈旧告警/回收——对本地触发的任务同样适用（它们入账后就是普通任务行，走同一套状态机）；§9 事项级复查（later）本草案不改：其触发条件是账本内任务的状态与标记，属账本派生而非节点计划，仍由 hub 扫表处理；后续如需再议，另行立项。
- **Rules 表**：Schedule / Text / Last_Fired 三列自切换起停用（hub 不再读写）。本草案不要求删列；删列与选项清洗另行批次处理。存量计划行在迁移时置 Enabled=No 防双跑（见 §8）。

## 7. 协议节点（无守护进程，如 grokbot）

本地调度是守护进程节点的能力。协议节点如需定时自触发，由其宿主环境自行实现，但入账格式（§4）必须一致。本草案不要求协议节点实现，不改变其现行写表口径。

## 8. 迁移步骤（以现存唯一计划 SCHED-HUB-MORNING 为首例）

1. 各节点实现本地调度并通过 §9 验收后，再切生产。
2. 切换顺序（防同期双跑）：先将 Rules 中 SCHED-HUB-MORNING 的 Enabled 置 No → 再在 hub 的 node 角色配置目录落 `schedules.json`（id 沿用 `SCHED-HUB-MORNING`，cron `50 8 * * *`，cap=`agent`）并锚基线 → 次日 08:50 验证本地触发与入账。
3. 幂等键格式变化：旧键 `sched:SCHED-HUB-MORNING:<期次>` → 新键 `sched:hub:SCHED-HUB-MORNING:<期次>`（多了 Node_ID 段，支撑 §2 第 4 条的多节点同计划语义）。切换在期次之间完成，不存在同期双键问题。

## 9. 验收用例（实现方自测并交回结果）

- T1 准点：测试计划每 3 分钟一期，节点存活时连续 3 期触发偏差均 ≤60 秒，无漏无重。
- T2 重启补期：停守护跨过一期后重启，只补最近一期且只补一次。
- T3 hub 停机：hub 守护停止期间期次到达，节点照常执行并入账；hub 恢复后账本完整可见。
- T4 多节点同计划：两个节点各挂同 id、同 cron，各产生一行独立记录（幂等键含各自 Node_ID），互不干扰。
- T5 审批：计划所指 cap 带 approval_class，到点先入 auth-required；驳回不执行，批准才执行。
- T6 基线：新建计划与修改 cron 后，首轮只锚基线、不触发。
- T7 时区：cron 按 node.json 的 tz 墙钟触发；将宿主机 TZ 改为 UTC 后行为不变。
- T8 陈旧：本地触发的任务卡在 working 且无心跳时，现行陈旧告警/回收照常生效。

## 10. 并入标准的动作（实现完成时执行）

- standard.md §7 删除现行定时调度段落，换入本草案 §2–§6 的规范表述；§10.1 第 7 条改写为账本派生职责（later 复查、陈旧观察等），不再含建单型调度；修订记录新增一条（建议版本 v3.6）。
- CHANGELOG 顶部加条目；守护版本号按仓库发版纪律 bump（package.json、package-lock.json、DAEMON_VERSION 三处同步）。
- doctor 增检：`schedules.json` 存在时，校验每条计划的 cap 在本节点 commands.json 中存在、cron 可解析、tz 合法；校验不通过只告警、不阻断守护启动（本地调度对该条停用）。
